# 테마 플레이리스트 (상황·분위기 추천)

"비 오는 날", "운동" 같은 **정해진 테마**를 고르면 그 분위기의 곡 50개를 돌려주는 API. 소비자는 **모바일 앱**(웹 화면 없음).
영상 모드 기반 — 결과는 유튜브 `videoId` 목록이고 우리 `Song` 카탈로그와 무관하다(벅스에 없는 곡도 나온다).

## 왜 이 방식인가 (검토한 대안과 탈락 이유)
2026-10-17 검증. 상세 수치는 `docs/WORK_LOG.md` 같은 날짜 항목.

## 수집 알고리즘 (`server/services/themeCollector.js`)
1. **검색**: 테마의 검색어마다 유튜브 플레이리스트 검색(`sp=EgIQAw%3D%3D`) 상위 10개 → 중복 제거
2. **곡 수집**: 각 플레이리스트 페이지의 `ytInitialData`에서 영상 목록(첫 페이지 최대 100개)
3. **거르기**: 8분 초과(1시간 모음 영상 — 수집 항목의 절반가량)·90초 미만·"플레이리스트/모음" 제목 제거
4. **곡 묶기**: 같은 곡의 MV·가사영상·Topic 음원을 하나로.
   - 제목 키: 꼬리표(`[MV]`, `Official`, `가사` …) 제거 후 본제목 / 괄호 속 별제목 / 한글만 / 영문만
   - 🔴 **제목 키 + 아티스트가 둘 다 맞아야 같은 곡** — 제목만 보면 에픽하이 〈우산〉과 윤하 〈우산〉, 태연 〈Rain〉과 BTS 〈Rain〉이 합쳐진다(1차 검증에서 실제로 발생)
   - 아티스트 추출: `아티스트 - 제목` / `아티스트 '제목'` / `[아티스트] 제목` / Topic 채널명 / 공식 채널명. **레이블 채널(STONE MUSIC, 1theK, SMTOWN …)은 아티스트로 안 쓴다**
   - 별칭 학습: `헤이즈 (Heize)`처럼 한·영이 같이 적힌 표기에서 `헤이즈 = heize`를 배운다
   - 대표 영상: Topic > 공식 채널 > 많이 등장. 라이브·커버·안무연습·리액션은 감점
5. **점수**: 곡 점수 = 등장한 플레이리스트 가중치의 합
   - 플레이리스트 가중치 = `(제목이 테마와 맞으면 1, 아니면 0.3) × (팝송·재즈·로파이 등 해외성향 0.3) ÷ log2(2 + 곡수/10)` — 큰 잡탕 리스트의 한 표는 가볍게
   - **해외곡 0.5배**: 한글 흔적이 없고 주로 해외성향 리스트에서 나온 곡. 빼지 않고 조금만 들어오게 (사용자 결정)
6. **등급**: `core` = 2개 이상 리스트에 등장(합의된 곡) / `explore` = 1회 등장이지만 **테마 제목이 맞는 국내 리스트 출신 + Topic·공식 영상**인 곡(AI 생성 채널·엉뚱한 아이돌 플리 출신을 거르려고)
7. **테마 특이성**: 〈밤편지〉처럼 어느 테마에나 나오는 곡을 깎는다. `share = 등장 리스트 수 / 그 테마 리스트 수`, `spec = 이 테마 share / 전 테마 share 합`, **최종 점수 = 점수 × √spec**. 다른 테마의 share는 이번 실행분 또는 DB에 저장된 값을 쓴다
8. **품질 게이트**: 이번 수집의 `core`가 **50곡 미만이면 그 테마는 DB에 쓰지 않는다** — 차단·빈 응답으로 망가진 수집이 기존 풀을 덮어쓰는 걸 막는다(유튜브는 예외 대신 빈 결과로 막는다 — `CRON_EXTERNAL.md`)

## 갱신 방식 = 누적 + 감쇠 (B안)
- 갱신할 때 **새 점수 = max(기존 점수 × `0.5^(경과일/45)`, 이번 점수)** (반감기 45일). 이번 수집에 안 보인 곡은 감쇠만
- 꾸준히 나오는 곡은 남고, 새로 뜨는 곡은 바로 들어오고, 안 보이게 된 곡은 서서히 빠진다. 수집이 한 번 실패해도 풀이 남는다
- 🔴 **합(+)이 아니라 max인 이유**: 합으로 하면 ① 같은 날 재실행하면 점수가 두 배로 부풀고 ② 점수 규모가 주마다 커져서 삭제 기준(`0.05`)이 의미를 잃고 ③ 신곡이 누적된 기존 곡을 몇 달간 못 따라잡는다. max는 재실행해도 결과가 같다
- 점수가 `0.05` 미만으로 떨어진 곡은 삭제 (탐색곡 점수 0.3 기준 약 4개월 미등장)
- 🔴 **기존 행 찾기는 `songKey` → 없으면 `videoId`**. `songKey`에 들어가는 아티스트 별칭(헤이즈=heize)은 **그 실행에서 수집한 데이터로만 학습**돼서, 전 테마 실행과 `--theme rain` 단독 실행의 키가 달라진다. 키로만 찾으면 같은 곡이 새 행으로 쌓인다(2026-10-17 실측: rain 단독 재실행에 17곡 중복). 수정 후 재실행 3회 모두 신규 0·행 수 불변
- 대안이었던 "스냅샷 통째 교체"는 매주 결과가 출렁이고 실패 시 그 주 리스트가 망가져서 탈락

## 50곡 구성 (`themeService.buildList`)
| 칸 | 수 | 뽑는 법 |
|---|---|---|
| 대표곡 | 15 | `core` 점수 상위 15 — **항상 포함**, 순서만 섞음 |
| 핵심 | 20 | 나머지 `core`에서 점수 비례 가중 랜덤 |
| 탐색 | 15 | `explore`에서 균등 랜덤 — 매번 새로운 곡 |
- 해외곡은 전체 최대 5곡. 대표곡 2곡 사이에 탐색곡 1곡꼴로 섞는다
- 같은 `seed`면 같은 목록(앱이 "아까 그 목록"을 다시 그릴 수 있게). seed를 안 주면 서버가 정해서 응답에 넣는다
- 검증 시 새로고침 간 유지율 40% — 숫자(대표곡 15)만 바꾸면 조정된다. **앱에서 써보며 맞출 것**
- 업계 표준은 없다. 참고로 Spotify 테마 플리는 기간 고정 + 셔플, Smart Shuffle은 대략 3곡 중 1곡꼴로 추천곡 삽입 — 우리 구성은 그 중간

## 실행
```
node scripts/refresh-themes.js --dry-run            # DB 안 씀. 테마별 요약 + 50곡 샘플 출력
node scripts/refresh-themes.js --theme rain         # 한 테마만
node scripts/refresh-themes.js --cache <dir>        # 유튜브 응답 캐시 사용(재실행 시 요청 0)
node scripts/refresh-themes.js                      # 전 테마 수집 → DB 반영
```
- 전 테마 약 600요청, 요청 간 1~2초 → **약 30분**. 2026-10-17 실측: 572요청 중 실패 7(1.2%, 비공개·믹스 리스트), 차단 징후 없음
- 품질 게이트에 걸린 테마는 반영하지 않고 종료 코드 1 — 기존 풀은 그대로
- 정의에서 뺀 테마는 `Theme.active=false`(곡 데이터는 남는다). 테마 추가·수정은 `themeDefinitions.js`를 고치고 스크립트를 돌리면 끝 — API가 DB만 읽으므로 **배포가 필요 없다**

## API (상세는 `docs/API_ENDPOINTS.md`)
- `GET /api/themes` → `{ themes: [{ key, name, songCount, updatedAt, cover }] }`
  - `cover`: 그 테마 core 점수 1위(국내곡)의 썸네일. **앱 카드 그림용** — 앱이 테마별 그림을 하드코딩하지 않아서 테마를 추가해도(배포 없음) 카드가 저절로 그려진다. 1위는 수집 갱신 때만 바뀐다
- `GET /api/themes/:key?seed=` → `{ theme: {key, name}, seed, updatedAt, songs: [{ videoId, title, artist, duration, thumbnail, tier }] }` (50곡)
- 썸네일은 `i.ytimg.com/vi/{videoId}/hqdefault.jpg`로 만든다(저장 안 함)

## 모바일 앱 연동 (`dibe2-app`)
앱 개발자가 알아야 할 것. 엔드포인트 표·응답 필드는 `docs/API_ENDPOINTS.md` Themes 절.
1. **인증**: 다른 API와 같이 `Authorization: Bearer <JWT>` 필수(없으면 401). 앱은 이미 로그인 토큰을 쓰고 있으니 같은 토큰으로 호출
2. **화면 흐름**: 테마 목록(`GET /api/themes`) → 테마 선택 → `GET /api/themes/:key` → 50곡
3. **새로고침 / 재현**: 새로고침은 `seed` 없이 다시 요청. 화면 복원·"아까 그 목록"은 응답의 `seed`를 저장했다가 `?seed=`로 다시 요청하면 같은 목록이 온다(서버 풀이 갱신되기 전까지)
4. **재생**: 결과는 **유튜브 `videoId`뿐**(`Song`·벅스와 무관, `songId` 없음). 앱은 videoId를 **폰에서 직접 오디오로 추출해 백그라운드 재생**한다(유튜브 검색 결과와 같은 경로) — 임베드 불필요. 앱 쪽 재생 구조는 `d:\projects\dibe2-app\CLAUDE.md`부터. `songId`가 없어 재생수 집계·좋아요·가사는 붙지 않는다
5. **저장**: 마음에 드는 곡을 남기려면 기존 비디오 플레이리스트(`POST /api/video-playlists/:id/videos`)에 `videoId`·`title`·`thumbnail`로 넣으면 된다(같은 영상 기준 구조). `duration`은 이 API는 **초(숫자)**, 비디오 플레이리스트는 `"3:45"` **문자열**이라 변환 필요
6. **`tier`**: `core`(여러 리스트가 합의한 곡) / `explore`(탐색곡). UI에 굳이 노출할 필요는 없고, 나중에 피드백(넘김·좋아요) 수집 시 구분용
7. **배포**: API는 `dibe2` main 배포(Netlify) 후부터 운영 주소에서 호출 가능. 데이터는 이미 운영 DB에 있다

## 예정: 자동화 (지금은 로컬 수동)
Netlify 크론은 30초 제한이라 테마 하나(요청 약 70회 × 1~2초)도 한 번에 못 끝낸다 → **쪼개서 이어 하기**. 기존 가사·장르·유튜브 크론이 이미 "30초만큼 처리하고 다음 실행에서 이어서" 하는 패턴이다.
- `cron-themes.js` 20분마다: 갱신 시점(7일 경과)이 된 테마 하나 → 1회차 검색으로 할 일 목록 저장 → 2~N회차 플리 25초씩 → 마지막 회차 집계·반영
- 테마당 6~8회, 9테마 약 70회 → 20분 간격이면 하루 안에 한 바퀴. 요청이 분산돼 오히려 덜 의심스럽다
- 진행 상태 저장용 컬렉션 추가 필요. **"N일째 갱신 안 됨"이면 디스코드 알림** (크론은 조용히 죽는다)
- 데이터센터 IP 차단 위험은 `cron-youtube.js`가 이미 Netlify에서 유튜브 검색을 잘 하고 있어 크지 않을 것으로 본다. 요청량이 더 많으니 실제로 돌려 확인
- 다른 후보: GitHub Actions(비공개 레포 월 2,000분 무료, 주 30분이면 충분) / Vercel·CF 이전(❌ 이전 비용 대비 얻는 게 없다 — 거기도 실행 시간 제한이 있어 결국 쪼개야 함)
