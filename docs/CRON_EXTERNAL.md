# 크론잡 및 외부 연동

## 크론잡 (Netlify Scheduled Functions)
`netlify/functions/cron-*.js` — Netlify Scheduled Functions 사용. 스케줄은 UTC 기준.

모든 크론은 **`server/utils/runCron.js`로 감싼다** — 실행마다 `cronruns`에 기록(시작 시 `running` → 끝에 `ok`/`wiped`/`error`, 강제 종료면 다음 크론이 `timeout`으로)하고, `wiped`·`error`·`timeout`이면 디스코드 알림. 상세는 `DATA_MODELS.md`의 CronRun. 서비스 함수(`updateYoutubeUrls` 등)는 `{ target, filled, closed, failed, budgetHit }`를 돌려주고 바깥 에러는 다시 던진다(삼키면 기록이 `ok`로 남는다).

채움 크론은 차트 크론(08:00) **뒤에** 돈다 — 곡이 저장돼야 필드를 채울 수 있기 때문. 크론마다 30초를 따로 받으므로 분리할수록 하루 처리량이 는다.

| KST 시간 | UTC 스케줄 | 함수 파일 | 작업 |
|----------|-----------|----------|------|
| 매일 08:00 | `0 23 * * *` | `cron-chart.js` | Bugs 차트 크롤링 → Song 저장 → **Chart 갱신** → `markCharted()` (본체 `server/utils/chartCron.js`) |
| 매일 08:05 | `5 23 * * *` | `cron-chart-pop.js` | Bugs **해외** 차트(`day/pop`) → Song 저장 → PopChart 갱신 → `markCharted()`. 국내와 30초 예산을 나눠 쓰지 않게 따로, 채움 크론보다는 앞(그날 신곡이 같은 아침에 처리되게) |
| 매일 08:10 | `10 23 * * *` | `cron-lyrics.js` | lyrics 없는 곡에 Bugs 상세페이지에서 **가사 + 곡 길이(`duration`)** |
| 매일 08:20 | `20 23 * * *` | `cron-genre.js` | genre 없는 곡에 Bugs **앨범 페이지**에서 장르/스타일 |
| 매일 08:30 | `30 23 * * *` | `cron-youtube.js` | youtubeUrl 없는 곡에 YouTube 검색 → URL 저장 (**길이로 후보 판정**) |

🔴 **가사가 유튜브보다 앞이어야 한다**(2026-08-16에 뒤바꿈). 유튜브 매칭이 가사 크론이 채운 `duration`을 쓰기 때문이다. 순서를 되돌리면 신곡은 길이 없이 검색된다.

### 처리 순서 = 차트에 최근 오른 곡부터, 같은 시각이면 인기순 (`{lastChartedAt: -1, chartHits: -1}`)
차트 크론이 `markCharted()`로 차트 100곡에 `lastChartedAt`을 찍고 `chartHits`를 `$inc` 한다(**곡당 하루 1회**(KST) — 재호출·국내/해외 중복 등장은 안 센다, 2026-11-04~. bulkWrite 한 방 — 100곡 순차 update는 30초 예산이 아깝다). 뒤따르는 세 크론은 전부 이 순서로 정렬해서 집는다(`songService.CRON_ORDER`).

**2차 키(`chartHits`)가 필요한 이유**: 적재분은 `lastChartedAt`이 **차트 등장 '월' 단위**(수집 데이터의 `lastSeen`)라 같은 값이 무더기로 생긴다. 1차 키만으로 정렬하면 그 안에서는 삽입 순서가 이겨버려 인기순이 죽는다.

**정렬이 없으면 자연순(≈`_id`, 오래된 삽입분부터)**이라 대량 적재분이 앞을 막아 **오늘 차트 신곡이 몇 달 뒤에나 처리된다.** 가사는 lazy fill 이 있어 그나마 낫지만 **장르는 lazy 가 불가능**(추천이 곡을 누르기 전에 장르로 후보를 고름 → 없으면 후보에 안 뜸 → 아무도 안 눌러 영원히 안 채워지는 데드락)해서 **신곡이 추천에서 통째로 빠진다.**

`lastChartedAt`이 없는 곡은 뒤로 밀리는데, 신곡을 다 처리하고 남는 예산으로 갉아먹으면 되므로 의도한 동작이다. 덤으로 `chartHits`가 적재 시점 스냅샷에 머물지 않고 **매일 갱신되는 살아있는 인기 신호**가 된다. (`Song` 인덱스 `{lastChartedAt: -1, chartHits: -1}` — 곡이 13,723개라 없으면 느리다)

**실측(2026-07-17 적재 직후)** — 가사 크론이 집는 순서가 의도대로다:
```
1. 오늘도 빛나는 너에게 - 마크툽 (238회, 2026-07)
2. 사계 - 태연 (208회, 2026-07)
3. 뜨거운 여름밤은 가고 남은 건 볼품없지만 - 잔나비 (206회, 2026-07)
```

### ⚠️ 스케줄 함수는 30초 제한 (설정으로 못 늘림)
Netlify 기본값 — 동기 60초 / **스케줄 30초** / 백그라운드 15분. 실행 제한은 **설정 불가**. 타임아웃은 강제 종료라 `catch`가 안 돌아 그 실행 자신은 알릴 수 없다. → `cronruns`에 **`running`으로 남은 문서**가 증거가 되고, **2026-11-04부터 다음에 시작하는 아무 크론이 그걸 `timeout`으로 바꾸고 디스코드로 알린다**(`runCron`의 `reportTimeouts` — 1분 여유, 원자적 교체라 알림 1번). 하루 마지막 유튜브(08:30)의 타임아웃은 다음 날 08:00에 잡힌다.

### ⚠️ Netlify는 같은 크론을 최대 3번 겹쳐 부른다 (2026-11-04 발견)
**공식 문서엔 없고** Netlify 포럼 직원 답변(실패 시 재시도, 3번 시도 후 포기) + `cronruns` 실측으로 확인. 실측 패턴: **15초 안에 응답이 없으면 +15초·+30초에 다시 호출**(앞 실행이 아직 도는 중에 겹친다), **500으로 빨리 끝나면 몇 초 뒤 다시 호출**. 10초대에 끝나는 장르 크론은 1번만 돈다. 다만 11-04엔 15초 넘긴 실행도 대부분 1번이라 **동작이 일정하지 않다**. 끌 방법도 없다.
- 그래서 **크론 본체는 겹쳐 돌아도 안전해야 한다.** 차트 크론: `Song {title, artist}` unique 인덱스(같은 신곡 두 번 삽입 방지, `saveSongData`가 11000이면 다시 찾아 씀) + `markCharted`가 **곡당 하루 1회만** 셈(필터 조건이라 락 불필요). 채움 크론은 "비어 있는 곡"만 집어 원래 멱등에 가깝다(같은 곡을 두 실행이 같이 채울 수는 있다 — 결과 동일)
- 이전엔 실행마다 `chartHits +1` → **~3배로 부풀었다**(보정 안 함, `DATA_MODELS.md`)
- 부수 효과로 **11-03 "벅스 차트 0곡" 알림의 정체**: 3번 중 1·3번째가 벅스 연결 끊김(`ECONNRESET`, 11-04 로컬 재현)으로 실패, 2번째가 성공 → 차트는 정상이었다. 이제 `getBugsChart`가 1초 간격 3번까지 다시 시도하고, 끝내 실패하면 **진짜 원인을 담아 throw**한다(전엔 `[]`를 돌려 "0곡"만 남았다)

### ✅ 2026-11-04 해외 차트 타임아웃 — 원인과 수정
해외 신곡 16곡(평소보다 많음)이 들어온 날, 곡 저장 + 등장 기록까지 29초 → **차트 저장 직전에 강제 종료** → 하루 묵은 해외 차트가 나갔다(로컬에서 수동 복구).
- **주원인: `Song`에 `{title, artist}` 인덱스가 없었다.** 크론 한 번에 이 키로 ~200번 조회(곡 저장 100 + 등장 기록 100)하는데 매번 1.4만 곡 전체 스캔. 평소에도 21~29초로 경계에 붙어 있었다 → unique 인덱스 추가
- **순서 변경**: 곡 저장 → **차트 저장** → 등장 기록. 사용자에게 보이는 차트를 먼저 살린다
- **단계별 소요시간**을 `stats.ms`에 남긴다(`setup`·`fetch`·`save`·`chart`·`mark`) → 다음에 느려지면 어디인지 바로 보인다. 인덱스 효과를 본 뒤 `saveSongData` 일괄 조회·삽입 재작성 여부를 정한다(보류)
- 차트 크론 3함수(`saveSongData`·`updateChartData`·`markCharted`)가 **에러를 삼키지 않는다** — 삼키면 중간 단계가 실패해도 `ok` + 알림 없음이었다. 100곡 미만이면 파싱 실패로 throw(전엔 0곡만 걸렀고, 1~99곡이면 `updateChartData`가 조용히 TypeError로 끝났다)

### ⚠️ 조용한 죽음의 두 번째 경로 — per-song catch가 에러를 삼킨다
채움 크론(youtube/lyrics/genre)은 곡마다 `try/catch`로 감싸 한 곡이 터져도 다음 곡으로 넘어간다. 문제는 **전 곡이 실패해도 바깥 `try`는 성공**해 `200`을 반환하고, 바깥 `catch`의 알림이 **안 뜬다**는 것. 즉 "초록불인데 실제론 아무것도 못 채운" 상태가 가능하다(예: 대상 사이트가 IP를 차단한 날).

**그래서 한 실행이 전멸하면(`진행 0 + 실패>0`) `runCron`이 상태를 `wiped`로 기록하고 디스코드를 쏜다**(예전엔 서비스 안의 `alertIfWiped()` — await 없이 불러 실제로 안 나갔을 수 있다). `failed` 카운터는 throw뿐 아니라 **조용한 실패**(가사 `null`, 유튜브 빈결과, 앨범 fetch 실패)도 센다. 요약 로그(`N곡 채움 | M곡 닫음 | K곡 실패`)로 부분 실패도 보인다.

### ✅ 조용한 죽음의 세 번째 경로 — DB 연결 실패 (2026-08-22 막음)
`connectToMongoDB()`가 실패를 **`catch`에서 삼키고 정상 리턴**하던 시절엔, 크론이 연결 없이 작업으로 진입해 mongoose가 쿼리를 버퍼링하며 매달리다 **30초 타임아웃 = 강제 종료 = 알림 없음**으로 끝났다. Atlas가 흔들린 날 크론이 통째로 조용히 죽는 경로였다.

**이제는 연결 실패가 `throw`된다** → 크론 바깥 `try/catch`가 잡아 `sendErrorToDiscord`(당시 `sendErrorToSlack`)가 정상적으로 울린다. 각 크론이 이미 `try/catch`로 감싸고 있어 별도 수정은 없었다.

- 🔴 **유튜브 빈결과는 마커를 찍지 않는다.** 유튜브는 예외 대신 **빈 결과를 조용히 돌려주는** 식으로 막을 수 있는데(`fill-youtube.js` 주석 참고), 그때 `youtubeCheckedAt` 마커를 찍으면 멀쩡한 곡을 "영상 없음"으로 **영구 오염**시킨다. 그래서 **"아이템은 왔는데 2~6분짜리가 없음"일 때만 닫고**, 아이템 0개면 `failed`로 세어 다음 실행에서 재시도한다. 단 0개의 원인이 **연령 게이트**면 `youtubeGatedAt`으로 따로 닫는다(아래 YouTube 항목).

### 점검: `node scripts/cron-health.js` (읽기 전용)
프로덕션 크론 로그를 직접 못 보므로 **DB 상태로** 판단한다: 맨 위 실행 기록(`cronruns` — 상태·에러 원인·차트 크론 단계별 소요시간), 각 크론의 마지막 작업 시각(오늘이면 정상), 미처리 백로그(크론 쿼리와 동일 조건), 소진 ETA, 신곡 상위 100곡 커버리지. 크론이 조용히 죽었는지 의심될 때 먼저 돌린다.

**그래서 크론이 도는 함수는 전부 `CRON_BUDGET_MS`(22초) 시간 예산을 보고 스스로 멈춘다.**
곡 수가 아니라 **경과 시간**으로 끊는 이유: 대상 사이트가 느린 날에도 안 터진다. 못 끝낸 곡은 다음 실행에서 이어지므로 손실이 없다.

🔴 **예산은 함수 시작 시각부터 잰다**(`runCron`이 `task(startedMs)`로 넘김, 2026-10-31~). 전엔 서비스 함수 안에서 새로 재서 콜드 스타트·DB 연결(~2초)이 예산 밖이었고, 예산 안에서 멈췄는데도 함수 전체가 **28.1초**(유튜브 수동 실행 실측)였다. 예산 체크는 곡 사이에서만 하므로 마지막 한 곡(유튜브 ~2초)만큼 더 넘어간다 → 22초 + 한 곡 + 마무리 ≈ 25초.

**장르를 `cron-chart`에 안 붙인 이유**: 신곡 많은 날 앨범 요청이 30초를 넘기면 **곡 저장 자체가 실패**한다. 가사/유튜브와 같은 "저장 먼저, 필드는 나중에" 패턴으로 분리했다.

**대량 백필은 여전히 크론이 아니라 `scripts/`의 로컬 스크립트가 책임진다.** 크론은 하루치 신곡용이다.

### 유튜브 매칭의 곡 길이 대조 (2026-08-16 적용)
`songService.js` 세 군데(크론 `updateYoutubeUrls` / lazy fill `updateYoutubeUrl` / 관리자 `searchYoutube`)에 `120~360`이 하드코딩돼 있다. 한 군데만 고치면 나머지가 어긋난다.

**상한 방식의 두 가지 실패**(2026-08 아티스트 수집에서 실측):
- 6분 넘는 곡을 **영영 못 찾고** `youtubeCheckedAt`으로 영구히 닫는다 (`Mandrake` 6:09, `Faust` 6:19)
- 반대로 **라이브·다른 버전이 통과**한다 (`이방인` 원곡 3:53인데 온스테이지 라이브 4:08이 잡힘)

**대안**: 벅스 트랙 상세의 `재생 시간`을 `Song.duration`에 저장하고 ±5초로 대조. 정답의 길이차는 0~5초에 몰리고 라이브는 16초 이상으로 갈린다. **가사 크론이 어차피 트랙 상세를 받으므로 요청이 늘지 않는다.**

**적용된 것**(2026-08-16)
- `songService.js`의 `durationFits(songDuration, videoSeconds)` **한 곳**이 정책을 갖는다 — 길이가 있으면 ±5초, 없으면 기존 `120~360`. 크론(`updateYoutubeUrls`)과 lazy fill(`updateYoutubeUrl`)이 같이 쓴다
- `helper.getTrackDetail()`이 가사와 길이를 **한 요청으로** 준다. 가사 크론과 가사 lazy fill이 이걸 쓰므로 **`duration`은 요청 0회로 딸려온다**
- **크론 순서를 바꿨다 — 가사 08:10 / 유튜브 08:30**(전에는 유튜브가 08:10). 길이를 먼저 채워야 매칭이 쓴다
- 🔴 관리자 검색(`getYoutubeUrlsByYouTubeSearch`)은 **길이 필터를 아예 없앴다**(±5초도, 2~6분도 아님) — 사람이 직접 보고 고르는 화면이라 후보를 좁히지 않는다. 예전 상한 탓에 6분 넘는 곡은 손으로도 못 찾았다. 길이는 응답에 실어 화면에서 보고 판단한다

🔴 **백로그에는 효과가 거의 없다 (실측 2026-08-16)**: URL 없는 10,839곡 중 `duration`이 있는 건 **77곡뿐**이고, **유튜브 크론 우선순위 상위 200곡은 0개**다.
- 원인은 **두 크론의 진도 차**다. 가사는 하루 120곡, 유튜브는 40곡이라 가사 쪽이 3배 빨리 나아간다. 그래서 유튜브 크론이 만나는 곡은 **가사가 이미 끝난 곡**(상위 200곡 중 124곡은 가사 있음 / 76곡은 마커로 닫힘)이고, 그 곡들은 길이 수집이 없던 시절에 처리돼 `duration`이 없다. 가사 크론은 그 곡들의 상세를 **다시 받지 않으므로** 앞으로도 안 생긴다
- **신곡은 정상**이다 — 차트 08:00 → 가사(+길이) 08:10 → 유튜브 08:30 순서로 셋 다 처음 만나기 때문
- 백로그까지 살리려면 **로컬 백필 스크립트가 필요하다**(약 1만 요청). 안 하면 백로그는 계속 고정 상한으로 매칭된다

ⓐ·ⓑ는 위에 적용됐다. ⓒ(lazy fill)는 **당초 계획과 달리 길이를 쓴다** — `duration`을 DB에서 읽기만 하므로 요청이 늘지 않는다(예전 메모는 그 자리에서 길이를 받아온다는 전제였다). 상세는 `docs/WORK_LOG.md` 2026-08-16.

🔴 **반주(Instrumental)는 길이 대조로 못 거른다** — 원곡과 길이가 같다. 제목에서 `(Inst.)` / `Instrumental` / `[MR]`을 걸러야 한다.

### 못 채우는 곡을 닫는 마커 (`lyricsCheckedAt` / `youtubeCheckedAt`)
"찾아봤는데 없더라"를 기록해 재시도 대상에서 뺀다. 없으면 못 받는 곡을 **매일 다시 긁는다**(실측: 6곡이 **567일째** 재시도 중이었음). 곡이 적을 땐 안 드러나지만 **대량 적재하면 못 받는 곡 80개가 크론 앞자리를 막아 매일 그것만 하고 끝난다**(head-of-line) — 뒤쪽 진짜 곡엔 영원히 도달 못 한다.

**영구 실패에만 찍는다.** `helper.getLyrics`는 네트워크 실패면 `null`, 가사가 원래 없으면 `''`를 반환해 **이미 구분이 된다**. `''`일 때만 마커를 찍으면 네트워크 실패는 마커가 없어 자연히 다음 실행에서 재시도된다. `updateYoutubeUrls`도 같다 — **아이템이 왔는데** 2~6분 조건에 맞는 게 없으면 닫고, 검색이 터졌거나(`catch`) **아이템이 0개면**(빈결과 차단 가능성) 마커를 안 찍어 다음 실행에서 재시도된다.

`adult`(19금) 곡은 **성인 인증이 필요해 가사를 원리적으로 못 받으므로**(`bugs.ui.showLoginLayer()` / `adultcheckval`) 크론·lazy fill 양쪽에서 **시도 자체를 스킵**한다. 마커조차 필요 없다.

(같은 패턴이 `updateGenres`에도 있다: 앨범ID를 못 뽑으면 `genre: []`로 닫아 재시도 대상에서 제외)

### 제목 셀 파싱 (`parseTitleCell`)
벅스는 `[19금]` 배지를 **스크린리더용 숨김 텍스트로 제목 셀 안에** 넣는다:
```html
<button class="badge o19"><span class="blind">[19금]</span></button><a title="BAND">BAND</a>
```
`.title`을 통째로 `text()`하면 `"[19금]\nBAND"`가 되어 제목이 오염되고, 그 오염은 UI 노출로 끝나지 않고 **`{title, artist}`를 키로 쓰는 중복 판별**과 유튜브 검색어까지 번진다. **제목은 `.title a`에서만** 가져오고 19금은 배지 존재로 따로 잡는다(`adult`). 프로덕션 `helper.js`와 스크립트 `lib/bugs.js` 양쪽에 있다(의도적 이원화 — 프로덕션과 로컬 스크립트를 분리).

- ⚠️ **문자열(`^\[...\]`)로 배지를 지우면 안 된다.** `[드포즈 극장] 바그다드 카페`처럼 대괄호가 **진짜 제목**인 곡이 있다. **구분자는 개행** — 실측상 배지는 `[19금]\n` 243/243, `[권리없는 곡]\n` 62/62 전부 개행이 뒤따르고, 진짜 제목은 공백으로 이어진다(0/2)
- ⚠️ **`.title button`은 19금이 아닌 행에도 있다**(1페이지에 5개) — `.o19`로 좁힐 것
- 배지 종류는 `[19금]`과 `[권리없는 곡]` 둘뿐. 후자는 별도 플래그를 두지 않는다(제목 정리로 해결되고, 재생은 유튜브라 무관하며, 가사가 없으면 마커가 닫는다)
- 🔴 **이 버그가 실제로 중복을 만들었다**: 제니 `ExtraL`이 3/12에 `[권리없는 곡]` 배지를 달자 제목이 달라져 중복 판별을 통과 → 같은 곡이 두 문서로 박힘. 배지가 없었으면 스킵됐을 곡이다. `scripts/fix-dirty-titles.js`로 정리 완료(2026-07-17)

### lazy fill (youtubeUrl / lyrics)
곡 저장(08:00)보다 필드가 늦게 채워지는 갭에 눌린 곡은 **재생 시점에 즉석으로 채운다.** 크론만으로는 백로그를 다 채우는 데 수개월이 걸리는데, lazy fill 은 **사용자가 실제로 튼 곡부터** 채우므로 그 대기가 사실상 사라진다.

| | 진입점 | 트리거 | 소스 | 실측 |
|---|---|---|---|---|
| youtubeUrl | `songService.getYoutubeId` → `updateYoutubeUrl(_id)` | **재생의 필수 경로**(서버가 재생을 안다) | YouTube 검색 | 1.1초 |
| lyrics | `songService.getLyrics(id)` (`GET /api/songs/lyrics/:songId`) | **화면**이 부를 때만(서버는 재생을 모른다) | 벅스 트랙 페이지 | 671ms |

- 크론과 lazy fill 둘 다 "비어 있는 곡"만 고르므로 **먼저 채운 쪽이 상대의 대상에서 빠져** 중복 작업이 안 생긴다
- 🔴 **둘의 커버리지가 다르다.** youtubeUrl 은 **API 레벨 방어**라 앱(dibe2-app)도 수정 없이 보호되지만, **가사는 웹 화면 전용이다** — `store/player.js` 의 `setCurrentTrack` 이 곡 전환 때 부른다(2026-11부터 — 예전엔 항상 마운트된 `Playlist.vue` 의 watcher 였다. 어느 쪽이든 가사 화면을 안 열어도 나간다). 앱이 `/api/songs/lyrics` 를 부르면 그때 채워지지만, 안 부르면 앱에선 크론이 채울 때까지 가사가 없다
  - 서버에서 "진짜 재생 기준"으로 만들려면 `getYoutubeId` 에 가사 채우기를 붙여야 하는데, `await` 하면 **재생이 671ms 느려지고** fire-and-forget 은 **Netlify Functions 가 응답 후 죽어서 불가능**하다(`modules/cron.js` 가 죽은 코드인 것과 같은 제약). 재생을 막지 않고 화면이 병렬로 요청하는 현 구조가 이 환경에선 맞다
- "유튜브에 정말 없는 곡"에서 **멈출지 다음 곡으로 넘길지는 큐를 아는 클라이언트 몫**(서버는 큐를 모름)
- 🔴 **lazy fill 은 마커가 있어야 안전하다.** 마커 없이 붙이면 가사를 원래 못 받는 곡(19금 등)을 **누를 때마다** 벅스를 때리는 증폭기가 된다. 19금·마커 찍힌 곡은 긁지 않고 즉시 반환(실측 43~52ms)
- **장르/스타일은 lazy fill 이 불가능하다.** 추천/필터가 곡을 **누르기 전에** 장르로 후보를 고르므로, 없으면 후보에 안 뜨고 → 아무도 안 누르고 → 영원히 안 채워지는 자기참조 데드락. 그래서 장르는 크론+백필이 책임진다

  - 찍기 전엔 이 곡들이 매일 크론 맨 앞에서 예산을 먹어(실행마다 실패 7~8) 뒤쪽 곡이 하루 3~7곡밖에 안 채워졌다
